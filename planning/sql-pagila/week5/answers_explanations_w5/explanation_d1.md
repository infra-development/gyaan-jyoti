# Introduction

Until Week 4, most SQL problems were solved using a single query.

For example:

- Retrieve customers
- Calculate revenue
- Rank customers
- Find running totals

Now the business begins asking larger questions.

Examples:

- Which customers spend more than the average customer?
- Which films have never been rented?
- What is the average revenue generated by each store?
- Which products perform above average?

These questions cannot always be solved with a single straightforward query.

Sometimes SQL must calculate one result first.

Then use that result in another query.

This idea introduces **Subqueries**.

---

# Why Do We Need Subqueries?

Consider this business question.

> Display films whose rental rate is greater than the average rental rate.

Before comparing every film,

SQL must first calculate:

```
Average Rental Rate
```

Only after knowing that value can SQL decide which films satisfy the condition.

The solution naturally becomes two steps.

```
Average Rental Rate

↓

Compare Every Film

↓

Result
```

This is exactly what a subquery does.

---

# Concept 1 - Scalar Subqueries (Q1–Q3)

A scalar subquery returns **one value**.

Examples include:

- Average payment
- Maximum payment
- Minimum rental rate
- Latest business date

Example:

```text
Average Rental Rate

↓

2.98

↓

Compare Every Film
```

Because only one value is returned,

it can be used with operators such as:

```sql
=

>

<

>=

<=
```

---

# Business Uses

Typical business questions include:

- Products above average price.
- Employees earning more than average.
- Customers spending more than average.
- Highest payment.
- Lowest inventory level.

Whenever the business needs **one calculated value**, think:

```
Scalar Subquery
```

---

# Concept 2 - Multi-step Thinking (Q1)

Consider this question.

> Display customers whose spending is greater than the average customer spending.

Many beginners try solving everything at once.

Instead, divide the problem.

```
Step 1

Customer Revenue

↓

Step 2

Average Customer Revenue

↓

Step 3

Compare

↓

Result
```

Professional SQL developers always think in logical steps.

---

# Concept 3 - Derived Tables (Q5–Q6)

Sometimes a single value is not enough.

Suppose you calculate revenue for every customer.

The result looks like a table.

| Customer | Revenue |
|----------|---------:|
| Mary | 186.55 |
| John | 152.43 |
| Lisa | 141.28 |

This temporary result can be treated like a normal table.

This is called a **Derived Table** (also known as an **Inline View**).

General syntax:

```sql
SELECT ...
FROM
(
    SELECT ...
) AS derived_table;
```

The inner query creates the temporary table.

The outer query uses it.

---

# Business Uses

Derived tables are useful whenever intermediate calculations are required.

Examples:

- Customer revenue
- Store revenue
- Monthly sales
- Product performance
- Intermediate reporting

Instead of repeating calculations,

build them once.

Then query the result.

---

# Concept 4 - WHERE Subqueries vs Derived Tables (Q7)

Although both contain nested queries,

their purpose is different.

### WHERE Subquery

```
Outer Query

↓

Needs One Value

↓

Filter Rows
```

The subquery supports filtering.

---

### Derived Table

```
Inner Query

↓

Temporary Table

↓

Outer Query
```

The derived table creates an intermediate dataset.

It is much more flexible.

---

# Concept 5 - Choosing the Right Technique (Q8–Q9)

Before writing SQL,

ask yourself:

## Do I need one value?

↓

Use a **Scalar Subquery**

---

## Do I need an intermediate table?

↓

Use a **Derived Table**

---

## Do I need to filter rows using calculated values?

↓

Use a **WHERE Subquery**

The business requirement determines the SQL technique.

---

# Concept 6 - Thinking Before Writing SQL (Q10)

Professional SQL developers rarely begin with SQL syntax.

Instead they ask:

```
Business Question

↓

Can this be solved directly?

↓

No

↓

Break Into Smaller Steps

↓

Choose SQL Technique

↓

Write SQL
```

This simple habit makes complex SQL much easier to build.

# Scalar Subquery vs Derived Table

| Scalar Subquery | Derived Table |
|-----------------|---------------|
| Returns one value | Returns multiple rows |
| Used for comparisons | Used as a temporary table |
| Common in `WHERE` and `HAVING` | Used in the `FROM` clause |
| Simple calculations | Intermediate business results |

---

# Common Mistakes

❌ Trying to solve the entire problem in one query.

❌ Using a scalar subquery when an intermediate table is required.

❌ Forgetting to give a derived table an alias.

❌ Writing deeply nested queries when the logic can be simplified.

❌ Thinking about SQL syntax before understanding the business problem.
